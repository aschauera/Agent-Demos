02   Inside the adapter: one request, one CRM session

After authentication + input validation
1

Log in

GET / POST Login

Uses server-held CRM credentials and language ID. Retains the returned session cookie.

2

Verify session

GET IsLoggedIn

Reuses the cookie. Requires an actual boolean true, with the configured wrapper if needed.

3

Execute operation

POST {configured method}

Forwards the JSON object, including WCF parameter wrappers. No guessed entity fields or URLs.

4

Attempt logout

GET Logout

Cleanup is attempted after Login, even on failure. Logout errors are logged and surfaced appropriately.

Request POST /api/operations/{operationName} · { "payloadJson": "..." }

Response { "resultJson": "..." } · JSON business errors remain in the CRM result.

Two credential boundaries

  • Adapter credentials live in the Power Platform connection; CRM credentials stay on the server.
  • All calls use one configured CRM service account. This is not delegated user access.
  • Fresh cookie jar per request; HTTPS certificate verification stays enabled.

Explicit failure behavior

  • Invalid auth, input, unknown operations, CRM failures, and timeouts return HTTP errors.
  • Do not blindly retry writes: a timeout or failed logout can follow a committed change.
  • Health checks the adapter only. Redact GET Login query strings in upstream logs.

Before going live

  • Configure the real CRM REST contract, credentials, trusted TLS certificates, and standard gateway.
  • Import the connector, enable gateway access, and test a read-only method against your CRM.
  • SOAP-only or additional IIS Windows authentication needs a different upstream integration.
